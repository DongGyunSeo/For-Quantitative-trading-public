# OKX API 추가 데이터 — 무엇을 얻을 수 있고 무엇을 푸는가 (2026-08-20)

지금까지 검증은 전부 OHLCV 만으로 했고, **그 한계가 반복해서 결론을 막았다.**
OKX 공개 API(인증 불필요)로 메울 수 있는 공백을 정리하고 수집기를 구현했다.

## 우리 미해결 질문 ↔ 데이터 매핑

| 미해결 질문 | 어디서 막혔나 | 필요한 데이터 | 우선 |
|---|---|---|---|
| 펀딩비를 **가정** 했다 (0/1/3bps) | 손익분기가 **7~13.7bps**. 가정이 결론을 좌우 | `funding-rate-history` | **1** |
| 청산 히트맵이 OI 넷팅 없이 거래량만 씀 (8중 계상) | 히트맵 3피처 중 2개 폐기, 1개는 기여 0 | `open-interest-history` | **1** |
| 캐스케이드를 레인지×거래량으로만 탐지 | 히트맵 소진량 필터 기여가 3회 실험 모두 0 | `contract-taker-volume` | **1** |
| 히트맵이 실제 청산과 얼마나 닮았나 | "근본 검증 불가" 로 남김 | `liquidation-orders` (WS 중심) | 2 |
| 청산은 mark price 로 트리거되는데 last price OHLC 사용 | 청산가 역산의 기준가가 틀림 | `mark-price-candles` | 2 |
| OOS 검증할 과거 구간 부족 | 구 CSV 세트 재업로드 필요 | `history-candles` | 2 |
| 포지셔닝 편향 미측정 | — | `long-short-account-ratio` | 3 |

### 왜 OI 이력이 가장 큰가

**가격 하락 + OI 급감 = 강제청산.** 가격 하락 + OI 증가 = 신규 숏 진입.
지금 우리 `detect_events` 는 이 둘을 구분하지 못한다. 히트맵으로 근사하려 했던 것이
바로 이 구분이고, OI 는 그걸 **직접** 준다. 상위1% 컷이 겨우 작동했던 이유가
"진짜 청산" 을 우연히 골라낸 것이라면, OI 로는 훨씬 깨끗하게 골라낼 수 있다.

### 테이커 볼륨이 두 번째인 이유

`buyVol`/`sellVol` 분리 → 일방적 공격 물량을 직접 잰다.
캐스케이드는 정의상 **한쪽으로 쏠린 테이커 매도** 다. 레인지×거래량은 그 대리변수일 뿐.

## 경로가 문서 판본마다 다르다 (하드코딩 금지)

같은 데이터의 경로가 세 갈래로 나온다:

| 데이터 | 후보 |
|---|---|
| OI 이력 | `/api/v5/rubik/stat/contracts/open-interest-history` (SDK) · `/api/v5/public/contract-open-interest-history` (문서A) · `/api/v5/trading-statistics/contract-open-interest-history` (문서B) |
| 롱숏비율 | `/api/v5/rubik/stat/contracts/long-short-account-ratio` · `/api/v5/public/margin-long-short-ratio` · `/api/v5/trading-statistics/long-short-account-ratio` |
| 테이커 볼륨 | `/api/v5/rubik/stat/contracts/taker-volume` · `/api/v5/public/contract-taker-volume` |

그래서 수집기는 데이터셋마다 **후보 경로 목록** 을 두고 런타임에 탐침한다
(`OKXClient.resolve_path`). 첫 성공을 캐시하고, 전부 실패하면 시도한 경로를
전부 담아 예외를 낸다. 문서가 또 바뀌어도 조용히 깨지지 않는다.

확정된 것:
- `GET /api/v5/public/funding-rate-history` — instId, after/before/limit, **1회 100건**
- 청산: **REST 이력 엔드포인트가 문서에서 확인되지 않음.** WS `ws/v5/public` 의
  `liquidation-orders` 채널이 주 경로. SDK 상수에는 `/api/v5/public/liquidation-orders`
  가 남아 있어 탐침 대상에 포함했다. → **소급 백테스트는 어려울 수 있고,
  전향 기록(forward recording)이 필요할 가능성이 높다.**

## 구현 (`qbot/data/okx.py`, `qbot/data/funding.py`)

- **주입 가능한 transport** — 기본은 표준 urllib, 테스트는 목 함수.
  네트워크 없이 페이지네이션·파싱·오류처리를 전부 검증했다 (24개 테스트).
- **페이지네이션**: OKX 이력은 최신순 반환, `after=ts` 는 "그보다 오래된" 레코드.
  end 에서 커서를 과거로 밀며 내려간다. **커서가 진행하지 않으면 즉시 중단**
  (서버가 같은 페이지를 반복해도 무한루프 안 남 — 회귀 테스트 있음).
- 구간은 **반열림 `[start, end)`**, 인덱스는 tz-aware UTC (프로젝트 표준).
- 응답 컬럼이 늘어나도 죽지 않음 (`extra0…` 로 흡수).
- `funding_bps` 파생, `taker_imb = (buy−sell)/(buy+sell)` 파생.

### 펀딩 부호 — 지금까지 가정이 틀렸을 수 있다

```
fundingRate > 0  →  롱이 숏에게 지급
funding_R = −(포지션 부호) × rate_bps / risk_bps   (정산 1회당)
```

**숏은 rate>0 일 때 받는다.** 우리가 살린 셋업은 **76%가 숏** 인데, 지금까지
"항상 지급(불리)"으로 계산했다. 실제로는

- 평상시(rate>0 우세) → 우리 숏 북은 **수취** → 지금 추정이 **과도하게 보수적**
- 폭락 직후(rate<0 기울기) → 숏이 지급 → 지금 추정이 맞거나 부족

캐스케이드 **직후** 진입이라는 셋업 특성상 후자 국면에 몰릴 가능성이 크다.
가정으로는 못 푼다 — 실측해야 한다. `qbot/data/funding.py::apply_funding` 이
거래별 정산 시각을 정확히 세어 R 단위로 붙인다 (부호 검증 테스트 10개).

## 실행 순서

```bash
# 1) 무엇이 실제로 되는지부터 (경로 + 이력 깊이)
python examples/okx_fetch.py --probe

# 2) 펀딩 실측 — 1순위
python examples/okx_fetch.py --funding --days 400

# 3) OI + 테이커 (5m 보존기간이 짧을 수 있음. probe 결과 보고 period 조정)
python examples/okx_fetch.py --oi --taker --days 90 --period 5m
```

**`--probe` 를 반드시 먼저.** rubik 계열 통계는 5m granularity 의 보존 기간이
짧아, 2023~2026 전 구간을 5m 로 못 받을 가능성이 높다. 그 경우 대안은
① 1H granularity 로 받아 근사 ② 지금부터 전향 기록 ③ 유료 데이터(Tardis 등).

## 예상 결과별 다음 행동

| probe 결과 | 다음 |
|---|---|
| 펀딩 OK (거의 확실) | 후보 3셋업에 실측 펀딩 적용 → 손익분기 7~13.7bps 대비 판정. **여기서 결론 남** |
| OI 5m 이 2023년까지 됨 | `detect_events` 를 OI 급감 기준으로 교체 → 히트맵 폐기 |
| OI 가 최근 것만 됨 | 최근 구간만 OI 로 재검증 (표본 작아도 방향 확인용) + 전향 기록 시작 |
| 청산 REST 불가 | 히트맵 근본 검증은 포기. WS 전향 기록 스크립트만 준비 |

## 한계 — API 로도 못 푸는 것

- 청산 **이력** 은 사실상 없다. 히트맵의 근본 검증(실제 청산과의 상관)은
  전향 기록 없이는 불가능.
- rubik 통계는 거래소 집계값이라 원시 체결 단위 재구성은 안 된다.
- OI 는 총량이라 롱/숏 분해가 안 된다 (롱숏비율로 간접 추정만).
