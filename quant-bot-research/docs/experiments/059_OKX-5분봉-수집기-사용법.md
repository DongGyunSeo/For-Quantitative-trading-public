# OKX 5분봉 수집기 — 사용법

`tools/okx_collect.py` · 로컬(Windows/macOS/Linux)에서 실행 · 의존성 `requests` 하나

```
pip install requests
```

## 왜 로컬에서 도는가

이 세션은 클라우드 샌드박스라 URL 을 직접 받아올 수 없다(환경 제약).
그래서 **수집은 사용자 PC 에서, 분석·검수·문서화는 여기서** 하는 분업이다.
이 프로젝트가 예전에 `collect_forward.py` 를 쓰던 방식과 같다.

## 확인한 API 한도 (2026-09 실측 교차검증)

| 엔드포인트 | 한도 | limit 상한 (문서) | limit 상한 (**실측**) | 용도 |
|---|---|---|---|---|
| `/api/v5/market/history-candles` | 20 req / 2s | ~~100~~ | **300** | 본 수집 |
| `/api/v5/market/candles` | 40 req / 2s | 300 | 300 | 최근 구간만 |
| `/api/v5/public/instruments` | 20 req / 2s | — | — | 종목 목록 |
| `/api/v5/market/tickers` | 20 req / 2s | — | — | 유동성 순위 |

### ⚠ 문서가 틀렸다 — probe 가 잡았다

OKX 공식 문서는 `history-candles` 의 limit 을 **"Maximum is 100; default is 100"** 이라고
적어 뒀다. 실측하면 **300 까지 그대로 준다**(101 을 요청하면 101 개가 온다).
`candles` 는 301 을 요청하면 300 으로 잘린다 — 그쪽은 문서대로다.

요청 수 기준 한도는 그대로이므로 이건 **처리량 3배**를 뜻한다.
그래서 수집기는 상수로 박지 않고 **시작할 때 한 번 재서**(`discover_limit`) 그 값을 쓴다.
나중에 OKX 가 다시 바꿔도 자동으로 따라간다. `--limit` 으로 덮어쓸 수도 있다.

한도 자체(20 req/2s)는 ccxt 가중치(base 100ms, history cost 1.0, candles cost 0.5)와
일치했고, 9 req/s 로 53회 호출 중 감속 0회로 확인됐다.

### 병렬 요청은 쓰지 않는다

한도는 **IP 에 묶인다.** 심볼을 나눠 병렬로 보내도 심볼마다 예산이 따로 생기지 않고
10 req/s 를 모두가 나눠 쓴다. 병렬로 처리량을 **늘릴 수는 없다.**

한 가지 여지는 있었다 — 직렬로 돌면 왕복 지연(~155ms) 때문에 6.5 req/s 에 머물러
한도(10 req/s)까지 틈이 남는다. 병렬로 그 틈을 메우면 9 req/s 까지는 간다.
하지만 20요청/2초 창에서 여유가 **35%(13/20) → 10%(18/20)** 로 줄어 버스트 한 번이면
넘친다. 3~4시간짜리 작업에서 1.4배를 얻자고 차단 위험을 질 이유가 없다.
→ **단일 스레드 + 전역 토큰버킷.**

### ⚠ 창을 두 개 띄우지 말 것 — 잠금 파일로 막아 뒀다

가장 흔한 실수다. `--only` 로 심볼을 나눠 PowerShell 창 두 개에서 돌리면
**각 프로세스가 자기 9 req/s 버킷을 들고 있어서 합계 18 req/s** 가 된다 —
한도를 나눠 쓰는 게 아니라 **넘는다**.

그래서 `collect` 는 시작할 때 `okx_data/collect.lock` 을 잡고, 이미 잡혀 있으면
**요청을 한 번도 보내지 않고** 거부한다.

- 수집 중 페이지를 쓸 때마다 하트비트를 갱신한다.
- 5분 넘게 갱신이 없으면(비정상 종료) 다음 실행이 넘겨받는다.
- 정상 종료·Ctrl-C·예외 어느 경우든 잠금을 푼다.
- 정말 다른 수집기가 없는데 막히면 `--force`.

### 처리량 산술

실측 왕복 지연이 ~155ms 라 **토큰버킷 9 req/s 에 닿지 못하고 6~7 req/s 로 돈다**
(probe 에서 history-candles 6.5 req/s, candles 4.2 req/s 로 측정). 지연이 병목이지
한도가 병목이 아니다.

```
300봉/요청 × 6.5요청/초 ≈ 2,000봉/초
5분봉 1년   = 105,120봉 ≈ 0.9분
5.3년       = 552,960봉 ≈ 4.6분  (재시도 여유 포함 6분)
50심볼 × 5.3년 ≈ 3~4시간      (문서값 100 이었다면 9~11시간)
```

심볼 간 병렬화로 6.5 → 9 req/s 까지 끌어올릴 수는 있지만(1.4배), 3~4시간이면
감수할 이유가 없다. 무인 실행 중 버그 위험이 이득보다 크다 — **단일 스레드를 유지한다.**

## 실행 순서

```bash
# 1) 한도·보존 깊이를 직접 재본다 (몇 분). 문서를 믿지 않고 확인하는 단계다.
python okx_collect.py probe

# 2) 심볼 선정 — 상장 중인 USDT 선형 영구선물을 24h 명목거래액으로 줄 세운다.
#    --min-list-date 이전에 상장한 것만 우선 뽑고, 모자라면 다음 순위로 채운다.
python okx_collect.py universe --top 50 --start 2021-04-02 --min-list-date 2021-04-02
#    50개가 안 채워지면 그냥 덜 뽑는다. 억지로 채우려면 --allow-short-history

# 3) 본 수집 — 중단해도 손해 없다. 다시 실행하면 이어서 간다.
python okx_collect.py collect
#    밤새 돌릴 수 없으면:  --max-hours 4   (나눠서 여러 번)
#    특정 심볼만:          --only BTC,ETH,SOL

# 4) 현황 확인 (언제든)
python okx_collect.py status

# 5) 마무리 — 정렬·중복제거·무결성 검사 후 gzip
python okx_collect.py verify
```

결과: `okx_data/raw/{심볼}_5m_futures.csv.gz` — 심볼당 약 **10MB**(원본 34MB).
컬럼은 기존 프로젝트와 **동일**하다: `time,open,high,low,close,volume`,
`time` 은 UTC 오픈 타임, `volume` 은 **`volCcy`(기준통화 수량)**.
기존 `BTC_5m_futures.csv` 를 확인해 맞췄다 — BTC 5m 중앙 167.7 BTC(일 $4.4B),
DOGE 10.0M DOGE(일 $472M)로 일치한다.

## 중단·재개가 안전한 이유

- 페이지마다 `{심볼}_5m_futures.part.csv` 에 **이어 쓴다**. 메모리에 쌓아두지 않는다.
- 재개하면 part 파일에서 **가장 오래된 ts** 를 읽어 그 지점부터 과거로 계속 간다.
- `manifest.json` 이 심볼별 진행 상태를 들고 있다.
- Ctrl-C 한 번 = 현재 페이지까지 저장하고 정상 종료. 두 번 = 즉시 종료.
- 목표 시작일을 나중에 더 과거로 바꿔도 이어서 내려간다(테스트로 고정).

## 한도를 넘었을 때

429 나 OKX `50011` 을 받으면 **속도를 절반으로 떨어뜨리고** 이후 성공할 때마다
2%씩 천천히 회복한다. 고정 sleep 보다 안전하고, 기본 속도의 20% 아래로는
내려가지 않는다. 종료 시 감속 횟수를 보고한다 — 이게 크면 `--rps` 를 낮춰라.

## 검수에서 확인하는 것

`verify` 가 심볼마다 보고한다.

| 항목 | 의미 |
|---|---|
| 행 | 총 봉 수 |
| 시작 / 끝 | 실제 확보한 구간 (상장일·보존한계로 목표보다 짧을 수 있다) |
| 공백 | 5분 간격이 빠진 봉 수 |
| 최장 | 가장 긴 연속 공백 |
| 이상봉 | high < low 처럼 말이 안 되는 봉 |

`미마감 봉(confirm=0)은 저장하지 않는다.` 마지막 봉이 진행 중이면 버린다.

## 검증

`tests/test_okx_collect.py` — **37개**. 네트워크 없이 가짜 OKX 응답기로 전부 돈다.

- 과거로 내려가는 페이지네이션이 정확히 5분 간격으로 빈틈없이 쌓이는가
- 미마감 봉이 빠지는가 / 보존 한계에서 멈추는가
- 서버가 같은 페이지를 반복해도 **무한루프에 빠지지 않는가**
- 중단 후 재개가 이어지는가 / 이미 끝난 심볼은 호출 0 인가
- 정렬·중복제거·공백 집계·이상봉 탐지
- 토큰버킷이 실제로 속도를 지키는가 / 감속·회복·하한
- **수집 결과가 프로젝트 로더로 바로 읽히는가** (`.csv.gz` 지원 추가)
- **두 번째 수집기가 요청 한 번 없이 거부되는가** / 오래된 잠금은 넘겨받는가 / 예외가 나도 잠금을 푸는가
- **limit 300 과 100 이 완전히 같은 데이터를 내는가** / 호출 수가 1/3 로 주는가
- 유니버스가 **토큰화 주식을 조용히 끌어오지 않는가** / 계약 수가 아니라 **명목가**로 줄 세우는가 / 역방향·정지 종목을 거르는가

전체 테스트 **224개 통과**.

## 유니버스 — 실측된 심볼 수

probe 결과 상장 중인 USDT 선형 영구선물이 **477개**(전체 SWAP 492개)다. 상장일 기준:

| 이전 상장 | 개수 |
|---|---:|
| 2021-07-01 | **54** |
| 2022-07-01 | 69 |
| 2023-07-01 | 86 |
| 2024-07-01 | 123 |

**`--min-list-date 2021-04-02` 을 권한다.** 54개가 2021-07 이전 상장이므로
2021-04 이전은 대략 50개 안팎이고, 그러면 **뽑힌 심볼 전부가 5.4년 전 구간을 덮는다.**

2022-07 컷을 쓰면 69개 중 50개를 고를 수 있어 여유롭지만, 그 심볼들은
**2021~2022 를 통째로 빠뜨린다**. 하필 4h FVG 의 엣지가 가장 강했던 구간이다.
그러면 "연도 효과" 와 "그 해에 어떤 심볼이 상장돼 있었나" 가 섞여 버린다.
연도별 부호 검사가 목적이므로 **전 구간을 덮는 쪽**이 맞다.

50개가 안 되면 그대로 덜 뽑는다(47개여도 기존 10개의 4.7배다).

## ⚠ 토큰화 주식 영구선물 (실물 목록 확인 중 발견)

OKX 는 지금 **AAPL·NVDA·AMZN·ASML·AMD·ADBE·ARM** 같은 **토큰화 주식 영구선물**을
상장해 두고 있다. 거래량이 커서 유동성 순위 상위에 들어오는데 **전부 2025~2026 상장**이라
이력이 몇 달뿐이다. 조용히 섞이면 "50심볼 × 5.3년" 이라는 전제가 깨진다.

그래서 `--min-list-date`(기본 2022-07-01) 를 못 채워도 **부족분을 유동성 순으로 채우지 않는다.**
정말 채우고 싶으면 `--allow-short-history` 를 명시해야 하고, 그때 어떤 종목이
언제 상장했는지 화면에 찍는다.

참고로 확인된 상장일: BTC·ETH·XRP 2019-11 · ADA 2020-02 · DOGE·ALGO 2020-04 ·
UNI 2020-09 · AAVE·1INCH 2020-12 · SOL 2021-01 · AGLD 2021-09 · APE·API3 2022-03 ·
APT 2022-10 · AR 2023-02 · ARB 2023-03.
**2021-04 이전 상장이 꽤 있으니 5.3년 목표는 현실적이다.**

## 전달

수집이 끝나면 `okx_data/raw/*.csv.gz` 를 대화에 첨부하면 된다.
한 번에 다 올릴 필요는 없고 배치로 나눠도 된다 — 로더가 `.csv` 와 `.csv.gz` 를
모두 찾고, 둘 다 있으면 압축본을 쓴다(`qbot.data.loader.symbol_files`).

`universe.json` 과 `manifest.json` 도 같이 올려주면 어떤 심볼이 왜 짧은지
(상장일인지 보존한계인지) 제가 바로 판별할 수 있다.
